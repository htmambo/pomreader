## 待办项

- [ ] **F-1 应用内存占用打点**：第三轮新增了第二个隐藏 BrowserWindow（CF 过盾专用，与渲染抓取窗口同 partition），必然带来内存增量。评审建议在后续版本增加内存占用打点，用于验证两窗口并存的开销是否可接受。
  **触发条件**：出现低配设备卡顿反馈，或用户主动询问内存占用。
  **备注**：CF 窗口是按需创建的（只有真遇到挑战页才建），非常驻；本轮未量化两窗口并存时的实际增量。

- [ ] **F-2 超大目录（>3000 章）的虚拟滚动方案重评**：第三轮 F14 只做了 `content-visibility: auto`（省排版与绘制成本），**DOM 节点数不变**（长篇仍是 2N 个节点）。当章数达到 10000+ 时，DOM 节点本身可能重新成为内存与渲染瓶颈。
  **触发条件**：真实用户出现万章级书籍且反馈目录打开卡顿。
  **备注**：若要做虚拟滚动，先解决第三轮记录的两个约束 —— CDK viewport 要求**确定高度**（`contain: strict` + size containment 使 `max-height` 失效），且目录是**双列网格**（需按行配对 + 重写 `:nth-child(-n+2)` 边框规则）。见主任务文档 F14 条目。

- [ ] **F-3 真实环境数据闭环**：第三轮的以下数字来自合成基准或结构性论证，未在真实打包产物上闭环：
  - 冷启动耗时（需真实用户库才有非空章节）
  - webview guest 在离开 `/search` 后的存活（Playwright 跑浏览器环境，无 Electron webview）
  - CF 过盾端到端（需真实挑战页与网络）
  - 3000 章真实书的目录端到端计时
  **触发条件**：下一个版本发布后。
  **备注**：结构性保证已写进代码注释（`searchVisited` 一次性 + `@defer` 只创建一次），但注释不是测量。

- [ ] **F-4 F10 行为变更的用户反馈跟踪**：重定向链超时预算累计化是**有意的用户可见行为变更** —— 此前总耗时可达声明值的 4 倍（书源代理声明 15s 实为 60s），现总耗时上界回到声明值。依赖超长跳转链的自建书源会从「挂 60s」变为「15s 正确失败」。
  **触发条件**：用户反馈「书源抓取超时」增多。
  **备注**：CHANGELOG 的 Performance 段已写明该变更与应对方式（调高该书源请求超时或换更快的源）。**不建议**回退到旧行为 —— 旧行为是「声明的超时从未兑现」的缺陷。
