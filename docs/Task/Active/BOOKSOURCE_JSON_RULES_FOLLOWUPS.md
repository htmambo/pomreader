## 表达力扩展（二期，按优先级）

- [ ] **T-1 ⭐ 目录分页 `tocPagination`**：目录分多页时循环抓取拼接。触发：遇到目录分页站点。表达力损失的最大头。
- [ ] **T-2 ⭐ 正文分页 `contentPagination`**：一章拆多页合并。触发：同上。
- [ ] **T-3 ⭐ 搜索二次跳转 `follow`**：搜索命中中转页 → 二次请求拿真实 bookUrl。触发：中转页型站点。
- [ ] **T-4 ⭐ 多候选规则**：`contentPattern` 等接受数组按序尝试（`string | string[]`）。替代手改 JS 的 try 多选择器。
- [ ] **T-5 ⭐ `responseType:'json'` + jsonpath**：兼容 legado API 型书源（当前被拒翻译的一大类）。需引入 jsonpath 求值器，先评估包体。
- [ ] **T-6 XPath 选择器**：CSS/正则都搞不定的顽固站点。低优先级。
- [ ] **T-7 签名/加解密能力**：时间戳签名、md5 参数。只能是内置参数化算法（不再走用户 JS），需单独安全评审。

## 引擎与运行时

- [ ] **T-8 ⭐ `encoding` 字段**（auto/utf-8/gbk 显式指定）。触发：代理层 auto 判错编码的站点出现。
- [ ] **T-9 `minDelayMs` 主链路强制限流**（现状仅镜像间限流）。触发：被站点限流/封禁的反馈。
- [ ] **T-10 P1.5 正则移 Web Worker**（可 terminate 强杀）。判据：出现 UI 卡顿报告或 ReDoS 源；v1 靠 guard 静态拦截兜底。
- [ ] **T-11 explore / 发现页规则**。触发：有真实需求（现状与 v1 均无）。
- [ ] **T-18 存量怪癖的两侧同修（P1 实施期登记）**。新引擎逐字复刻了旧模板的 4 处怪癖 —— 差分测试要求行为等价，单边"修好"就是制造漂移，故全部挂起。清单：
  ① **`.replace` 的 `$` 特殊模式**：`searchPath` / `rawBody` 里的 `{keyword}` 用 `String.replace` 字符串替换，关键词含 `$&` / `$'` / `$1` 时会被解释（`smart-rules.ts:698`、`:702-706`）。改为函数替换 / `split().join()`，**必须模板与引擎同时改**，否则差分立刻红。
  ② **`.replace` 只替换首个**：`{keyword}` 出现两次时第二个不替换。改法同上（`/g` 或 `split`）。
  ③ **正则无捕获组时产出 `undefined`**：`extractLinks` 假定组 1=href、组 2=文本，规则没写组时 `absUrl(undefined, base)` 会被 `new URL` 归一成 `.../undefined` —— 静默错 URL。要么引擎侧显式报错，要么模板侧补组数校验（选哪个取决于是否算"规则写错"，建议先报错）。
  ④ **`urls[0]` 不做镜像 failover**：多 `@url` 源只匹配第一个域名。方案 §3.1 已明确 v1 只取 `[0]`，与 T-2/T-3 表达力扩展一并考虑。
  触发：任一项在真实书源上被用户报障；或差分 fixture 库补到含这些形态的样本时。

- [ ] **T-19 手改检测的盲区：函数体内部（P3.1 登记）**。`checkPureTemplate` 只查**顶层**声明（白名单函数名 + 白名单常量名）。在白名单函数体**内部**加语句（改 `search()` 实现之类）检测不到，这类源会被当作纯模板迁移、用户手改静默丢失。
  要补就得逐函数体比对模板产物，而那正是方案 F15 否掉的方案（模板版本漂移会误伤大量合法源）。可选方向：① 维护一份"函数体指纹"表（按模板版本），比对失败才判手改；② 函数体里出现**白名单之外的新标识符**就判手改（需要一份沙箱运行时全局变量白名单）。
  现状是**已知取舍**，不是遗漏。触发：真实用户报"迁移后我改的规则不见了"。
- [ ] **T-20 `convert` 归档失败时 `.js` 残留无用户可见提示（P3.1 登记）**。`.json` 已落盘可用、`.js` 留在 `booksources/`（下次启动因同 uuid 判 skip，自愈），但用户**看不到**这件事 —— 主进程只 `console.warn`。若要暴露，convert 的返回值需从 `string` 改成 `{ fileName, archived }`，preload 类型 + 服务层报告同步改。P4 会删掉整条 channel，届时自动消失，故暂不做。
- [ ] **T-21 `tsconfig.app.json` 的 include 仍是手工名单**（P3 收口登记）。`header-parser.ts` 与差分基座 `legacy-runner.ts` 原本不在 tsc program 内 —— 既查不出类型错误，也导致 eslint 报 `parserOptions.project`。P3 已把这两个补进去，但名单本身仍是逐个手写：将来再出现"只在 vitest / worker 里被引用、不在 main.ts 可达图内"的文件，会再次静默逃过类型检查。根治方向是让 include 覆盖 `src/**/*.ts`（需先确认 worker 专用文件不会因此被错误打包），属 P4 tsconfig 清理一并做。
